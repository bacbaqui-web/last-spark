# 다수 적의 관절·그리기·충돌 계산 최적화

## 적용 내용

- 물리·AI·피해·배터리 시간은 기존 작은 단계로 모두 진행합니다. 전투 HUD는 해당 화면의 마지막 상태로 한 번 갱신하며, 발 접지 계산은 화면을 그리기 전으로 모읍니다. 사격의 실제 메시 검사, 화살/추적 조준, 근접 공격 자세와 사망 파츠 생성은 필요한 자세를 먼저 완성합니다. AI의 눈 위치, 총구와 상체 자세는 매 물리 단계에서 갱신합니다.
- 관절과 무기·로터처럼 움직이는 부분은 유지하고, 고정 장식/표면의 로컬 행렬 계산만 멈춥니다. 발 계산에서 공통 상위 좌표의 중복 갱신과 조준 시 전신을 재계산하던 부분을 제거했습니다. 전체 노드를 매번 비교하는 일반 캐시는 실제 브라우저에서 느려져 제외했습니다.
- 같은 종류의 적 부품은 `InstancedMesh`로 함께 그립니다. 원본 관절 메시·약점·총구는 그대로 유지하며 실제 렌더 구간에서만 원본 표면을 숨깁니다. 적 수, 원본 형상, 텍스처, 눈과 총구 섬광, 검은 파츠 사망 연출은 유지됩니다. 그리기 중 오류가 나도 원본의 표시와 좌표 갱신 함수를 복구합니다. 인스턴스 버퍼는 용량을 늘려 재사용하며 공유 형상과 재질을 해제하지 않습니다.
- 적 이동 및 밀집 분리의 벽 검사는 기존 공간 인덱스에서 주변 셀을 찾고 동일한 반경·높이·바닥 조건으로 판정합니다. 적끼리의 밀집 분리 순서와 이동 규칙은 바꾸지 않았습니다.

관련 구현: `frame-work.js`, `wild-enemy-models.js`, `enemy-render-batch.js`, `collision-broadphase.js`, `main.js`.

## 검증 방식

- 기존 구현 대비 5종 × 360프레임의 실제 관절 모델 전체 행렬 비교: 최대 차이 0.
- `verify-frame-work.mjs`: 5종 × 48프레임, 화면당 1~6회 물리 단계. 최종 자세·시계·총구·AI 눈 위치, 즉시 공격 자세, 사망 파츠 시작 위치, 중간 정리/오류 처리 검사.
- `verify-wild-enemy-game.mjs`: 기존 실제 게임 전투 검사에 물리 4단계의 시간 보존 및 HUD 1회 갱신 검사 추가.
- `verify-enemy-render-batch.mjs`: 80개체의 관절 행렬과 인스턴스 행렬, 머리 피격 거리/대상, 숨긴 적/부위, 총구/눈, 그림자 속성, 그리기 오류 복구, 버퍼 재사용과 사망 처리 검사.
- `verify-enemy-collisions.mjs`: 공간 인덱스와 전체 맵 검사의 결과 12,240건 비교. 셀/높이 경계, 높은 바닥, 맵 변경 및 초기화 포함.

## 실제 브라우저 비교

격리 Chrome, Apple M4, 1280×720, DPR 1, 균형 화질. 회수작전 3블록/시드 3040804531, 동일한 적 혼합·초기 난수·플레이어 위치·연속 미니건 사격, 오디오 없음. 고정 배치에서는 적을 제거하지 않고 80/120마리를 유지하며 15초씩 측정합니다. 연속 전투는 처치한 적을 재충원해 전체 120마리를 유지하며 30초 측정합니다. 각 경우 3초 준비 후 측정하며 전후 모두 같은 CPU 샘플러를 사용합니다.

프레임 진행과 처치/가림에 따라 전투 난수 소비와 실제 활성 수가 달라집니다. 고정 배치와 연속 전투 수치를 구분하고, 전체 표본 평균과 느린 프레임도 기록합니다. CPU의 렌더 명령 제출 시간은 GPU 시간과 다릅니다. 이 부하 시험은 장시간 실제 플레이나 모든 기기의 60 FPS를 보장하지 않습니다.

원시 파일: `output/crowd-performance/summary-final-before.json`, `summary-final-after.json`, 각 경우의 JSON/CPU 프로파일. 전후 코드 스냅샷은 `output/frame-work-before/source/`에 보존합니다.

같은 전투 프레임을 원본 렌더와 인스턴스 렌더로 다시 그린 비교에서, RGB 채널 차이 24 초과 픽셀은 전체의 **0.000326% (3픽셀)**였고 평균 채널 차이는 **0.00179 / 255**였습니다. 같은 화면의 그리기 요청은 **4,524 → 2,231**이었습니다. `recovery-render-comparison-final-after.json` 및 전후 PNG로 확인할 수 있습니다.


### CPU 샘플러 없이 같은 부하 비교

첫 기준 측정 `frame-work-before`와 배포 후보 `release-after`는 80/120마리 고정 12초, 연속 전투 25초로 같은 조건입니다. 각 조건 1회 측정이므로 기기 부하와 전투 진행에 따른 변동이 있습니다.

| 조건 | 평균 FPS 전 → 후 | 1% low FPS 전 → 후 | 계산 ms 전 → 후 | 렌더 제출 ms 전 → 후 | 마지막 그리기 요청 전 → 후 |
|---|---:|---:|---:|---:|---:|
| 80마리 고정 | 34.79 → 42.28 | 19.97 → 16.36 | 17.24 → 13.77 | 10.43 → 8.80 | 3,253 → 1,757 |
| 120마리 고정 | 15.98 → 23.52 | 11.99 → 10.00 | 47.41 → 30.71 | 14.02 → 10.60 | 4,302 → 2,000 |
| 120마리 보충·연속 전투 | 24.30 → 26.87 | 8.07 → 7.92 | 23.32 → 21.84 | 16.61 → 14.05 | 4,304 → 2,238 |

고정 120마리에서 평균 FPS는 약 47% 증가했고, 그리기 요청은 약 54% 감소했습니다. 연속 전투의 실제 활성 적 평균은 **106.8 → 114.5마리**였습니다. **평균은 개선됐지만 1% low는 개선되지 않았고, 120마리 60 FPS도 달성하지 못했습니다.** 순간 지연과 장시간 플레이는 추가 과제입니다. 새 방식도 원래 형상을 모두 그리므로 삼각형 수는 고정 120마리 약 415만 개로 유지됩니다.

CPU 샘플러를 켠 보조 비교(`final-before`/`final-after`, 고정 15초·연속 30초)는 평균 FPS가 80마리 **25.19 → 42.04**, 120마리 **8.99 → 24.71**, 연속 전투 **18.44 → 28.91**이었습니다. 도구 오버헤드와 시간대별 부하 영향이 있어 위의 일반 측정과 섞어서 효과를 계산하지 않았습니다. 모든 브라우저 실행에서 오류는 0건이었고, FPS 표시의 일시정지/재개와 390px 화면의 겹침도 검사했습니다.

재현 예시:

```sh
CROWD_COUNTS=80,120 CROWD_SECONDS=12 CROWD_LIVE_SECONDS=25 CROWD_MODES=recovery CROWD_LABEL=release-after PLAYWRIGHT_MODULE=/path/to/playwright/index.mjs node scripts/profile-enemy-crowds-browser.mjs
```

이전 버전 비교는 `CROWD_BASELINE_DIR=output/frame-work-before/source`를 추가합니다. 이 디렉터리는 기준 커밋 `d73068e`의 `main.js`, `wild-enemy-models.js`, `sortie-runtime.js` 원문을 담습니다. CPU 샘플은 `CROWD_PROFILE=1`, 동일 화면 전후 비교는 새 버전에서 `CROWD_RENDER_CHECK=1`로 켭니다. 테스트 주입 코드는 정식 번들에 포함되지 않습니다.
