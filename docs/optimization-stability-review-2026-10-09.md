# LAST SPARK 최적화와 안정화 검토

2026년 10월 9일 기준으로 가장 먼저 해결할 문제는 **저장 데이터 보호, 빠른 이동의 벽 관통, 실제 게임 경로를 검증하는 배포 검사**입니다. 성능 개선은 **불필요한 렌더링 중단 → 충돌 데이터 축소 → 구역별 생성과 검사 → 메시 묶기** 순서가 적절합니다. 해상도와 이펙트 품질 조절은 그다음 단계입니다.

기준은 `main`의 `e58d6de`와 현재 미커밋 변경을 합친 작업 폴더입니다. 이번 작업은 진단, 재현 코드, 개선 계획을 추가했습니다. 게임 동작과 기존 작업 파일은 수정하지 않았고 배포하지 않았습니다. 아래 개선 항목은 적용 완료 목록이 아닙니다.

## 먼저 해결할 안정성 문제

### 저장 데이터가 손상되거나 저장할 수 없을 때

`salvage-campaign.js:24–38`은 일부 최상위 데이터만 검사한 뒤 추가 필드를 바로 사용합니다. 다음 문제가 재현됐습니다.

- `clearedStages: {}`는 `.filter`, `stashWeapons: {}`는 `.forEach`, `weaponSlots: {}`는 `.slice`에서 예외가 발생합니다.
- 빈 `frames`는 로딩을 통과하지만 `frame()`이 없습니다. 존재하지 않는 무기 타입도 로딩을 통과합니다.
- JSON 전체를 읽지 못하면 새 캠페인을 만들고 바로 저장하여 원래 데이터를 덮어씁니다.
- `setItem`이 실패해도 출격은 성공하고 메모리의 탄약과 출격 상태는 변경됩니다. `storageError`는 있으나 현재 본거지 UI에 이를 알리는 처리가 없습니다.

**대책:** 저장 스키마를 버전별로 검사하고 복구한 뒤 적용합니다. 모든 배열·아이템 타입·유한 수치·수량·기체 ID·선택 ID를 검증합니다. 손상된 원본은 별도 키나 내보내기로 보존하고, 마지막 정상 저장본을 복구할 수 있게 합니다. 출격·귀환·장비 변경은 새 상태를 구성하고 저장 성공을 확인한 다음 확정하는 방식으로 바꿉니다. 저장 실패가 발생한 귀환은 결과를 유지하며 다시 저장할 수 있어야 합니다. 여러 탭의 동시 출격에는 저장 revision과 탭 소유권 검사를 둡니다.

출격 중 새로고침하면 기체를 잃는 현재 게임 규칙과 기술적 저장 실패를 구분해야 합니다. 임의의 자동 부활이나 이어하기를 추가하는 방식으로 처리하지 않습니다.

### 빠른 이동 중 얇은 벽 관통

`player-movement.js:11–22`의 `streetCollision` 분기는 기존 박스 충돌의 연속 이동 검사를 사용하지 않습니다. `street-walk-collision.js`는 이동 후 위치의 몸통 충돌을 확인합니다. 시작점 `(0, 1.7, 0.6)`에서 종점 `(0, 1.7, -0.6)`으로 이동하면 가운데 두께 0.1m 벽을 통과합니다. 이는 속도 30m/s에서 40ms 한 프레임에 해당합니다.

**대책:** 거리 맵에도 캡슐의 연속 충돌 검사를 적용합니다. 먼저 이동 거리를 몸통 반경보다 충분히 작은 간격으로 나누는 제한된 서브스텝을 적용하고, 장기적으로 swept capsule과 충돌 트리를 연결합니다. 벽뿐 아니라 천장·경사·계단·자동차·잔해를 검증하고, 원래 허용한 잔해 등반 높이는 유지합니다. 위치가 유효하지 않을 때는 마지막 안전 위치로 복구합니다.

완료 조건은 30/60/120FPS와 100–250ms 프레임 지연, 대시·칼 돌진·점프에서 관통과 지하 낙하가 없고, 벽 미끄러짐과 잔해 이동이 유지되는 것입니다.

### 포커스 상실과 그래픽 장치 오류

`main.js:446`에는 blur 때 입력을 비우는 처리가 있습니다. 그러나 Pointer Lock 대체 모드에서는 실제 잠금이 없으므로 `exitPointerLock`에 따른 정지 이벤트가 발생하지 않으며, blur 처리도 `active=false`를 지정하지 않습니다. `visibilitychange`와 게임 수준의 WebGL context loss 복구 흐름은 없습니다. `main.js:502`의 프레임 루프는 update나 render에서 예외가 나면 다음 프레임 예약에 도달하지 못합니다.

**대책:** 일시정지 함수를 하나로 통합해 blur, 숨겨진 탭, Pointer Lock 해제, context loss가 같은 입력·오디오·시간 처리로 연결되게 합니다. 복귀 시 누른 키와 발사 상태를 초기화하고 프레임 기준 시간을 재설정합니다. 그래픽 context 복구 후 재질·장면을 검증하고 사용자 입력으로 재개합니다. 치명적 예외는 전투를 정지하고 복구 UI와 오류 기록을 제공하며, 망가진 상태를 무한 재시도하지 않습니다. Three.js 자체의 context 복구 기능과 게임 진행 중단 정책은 별개입니다. [Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API), [WebGL context loss](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/webglcontextlost_event).

**대책:** 검사 목록과 실행 명령을 일원화하고 현재 게임과 구형 도구 검사를 구분합니다. 배포 전에 현재 모드의 단위·통합·브라우저 검사를 통과시킵니다. `main.js` 문자열을 바꿔 VM에서 실행하는 테스트는 점진적으로 순수 게임 상태 함수와 실제 브라우저 통합 검사로 대체합니다. 연결 지도 생성, 출격, 사격, 보스, 회수, 귀환, 손실, 다시 출격까지 한 흐름으로 검사해야 합니다.

| 14 | HUD와 레이더 업데이트 분리 | 시간·적 수·무기명은 값이 변할 때, 레이더는 우선 10–20Hz로 갱신합니다. `updateSlotHUD`에는 이미 HTML 차이 검사가 있으므로 그 점을 유지하면서 문자열 생성·DOM 직렬화 비교도 상태 기반으로 줄입니다. 조준점과 즉시 타격 피드백은 렌더 주기를 유지합니다. |

| 17 | 품질 단계와 동적 해상도 | 저/중/고에 DPR, 그림자, 식생, 파편 수를 묶고 프레임 예산에 따라 천천히 조절합니다. 해상도를 매 순간 출렁이게 하지 않으며 적 식별, 사격 판정과 반응 시간은 공통으로 유지합니다. |

메시 병합과 인스턴싱은 draw call을 줄이는 공식적인 Three.js 최적화 경로입니다. [Three.js 객체 최적화](https://threejs.org/manual/pages/optimize-lots-of-objects.html). BVH 후보는 [three-mesh-bvh 공식 저장소](https://github.com/gkjohnson/three-mesh-bvh)이며, 설치·통합은 하지 않았습니다. 적용 전 Three.js 0.180과 인스턴스·변형 메시의 호환성을 검사해야 합니다.

## 로딩과 배포 용량

- 로컬 `dist`에 약 52.85MiB와 52.87MiB의 원본 ZIP이 복사됐습니다. 합계 약 105.72MiB입니다. 두 파일은 현재 미추적 파일이므로 이 결과가 현재 공개 배포에도 ZIP이 있다는 뜻은 아닙니다. 원본 보관 폴더와 public 런타임 폴더를 분리하거나 배포 자산 허용 목록을 둡니다. ZIP은 시작 시 요청되지 않았으므로 이를 제외하는 것만으로 첫 화면이 106MB 빨라진다고 볼 수는 없습니다.
- 시작 때 적 GLB 5개가 약 29.57MB, 약 28.2MiB 전송 데이터로 로드됐습니다. 공통 텍스처 중복을 제거하고 필요 모델의 선택 로딩, Meshopt/Draco, KTX2/Basis를 비교합니다. 파일 압축률과 디코딩 시간·GPU 메모리를 함께 측정합니다.
- 큰 JS는 TPS 약 1.92MB, 로봇 약 1.09MB, Three 약 595kB입니다. 동작/리그 JSON과 편집용 데이터의 초기 의존성을 추적하고 현재 게임에 필요한 클립만 먼저 로드합니다. 단순히 chunk 경고 임계값을 올리는 것은 성능 개선이 아닙니다.
- `game-bootstrap.js`의 전체 preload가 끝나야 main이 실행됩니다. 개별 실패의 fallback은 이미 있으나 시간 제한·진행률·재시도 화면이 없습니다. 본거지 UI를 먼저 보여주고 필수 에셋 실패와 장식 에셋 실패를 구분합니다.
- production에 편집기·갤러리까지 모두 빌드하는 현재 구성은 게임용과 개발도구용 엔트리로 구분할 수 있습니다. 다만 사용 중인 페이지는 삭제하지 않고 별도 배포나 선택 빌드를 제공합니다.
- 릴리스에서 복원하는 외부 런타임 ZIP은 버전·체크섬·필수 파일 목록을 확인합니다. 배포 검사는 하위 경로 URL, GLB·텍스처 404, MIME, 이전 캐시와 새 manifest의 혼합까지 확인해야 합니다.

## 메모리와 자원 수명

`disposeStreetBlock`과 적 파괴 효과의 정리 코드는 이미 존재합니다. 같은 지도 두 번의 생성 검사에서도 대부분의 소유 geometry/material에 dispose 이벤트가 발생했습니다. 현재 게임을 자원 정리가 전혀 없는 구조로 평가하면 부정확합니다.

추가로 다음을 정리해야 합니다.

1. `recovery-drone.js:6–8`은 생성마다 TextureLoader로 텍스처를 만들지만 `disposeStreetBlock`은 material과 geometry 중심으로 정리합니다. Material을 dispose해도 Texture는 자동 해제되지 않습니다. 1536×1024 이미지 한 장은 RGBA와 mipmap을 단순 가정하면 약 8MiB입니다. 공유 텍스처 캐시 또는 명시적 texture 소유권이 필요합니다. [Three.js 자원 해제](https://threejs.org/manual/pages/how-to-dispose-of-objects.html).
2. 생성 후 출발 구역에서 제거하는 나무·차량은 장면에 붙지 않아 나중의 traverse 정리 대상에서도 빠질 수 있습니다. geometry 공유 여부와 차량별 material 소유권을 구분해 제거 시 정리합니다.
3. `frame-preview.js`의 base64 이미지 Map은 크기 제한이 없습니다. 외형 조합을 계속 늘리면 캐시도 늘어납니다. 최근 항목 제한, 명시적 초기화, 필요시 Blob URL 회수 정책을 둡니다.
4. 맵을 바꿀 때 이전 collision 배열·surfaces·업데이트 closure·scene 참조가 함께 교체되는지 확인합니다. 구역 단위 ResourceTracker로 texture/material/geometry/instance/physics/이벤트/오디오 소유권을 정리하되 공유 자산은 중복 dispose하지 않습니다.
5. 30회 출격·귀환, 100회 장비 교체, 다수 적 파괴 후의 안정 구간 heap·texture·geometry 수를 비교합니다. 강제 GC 지원 여부와 캐시 예열 상태를 기록하고 단일 순간의 큰 heap을 누수라고 판정하지 않습니다.

## 게임 진행과 적 배치 안정성

브라우저에서 시작한 STAGE 1의 계획상 일반 적은 `blocks 2 × enemyCount 2`로 4마리지만, 해당 실행의 실제 생존 적은 일반 2마리와 보스 1마리였습니다. `spawnRoadGroup`은 160회 후보 배치에 실패하면 조용히 건너뜁니다. 블록이 연결돼 있어도 적 수와 보행 가능성이 보장되는 것은 아닙니다.

생성 시 플레이어 캡슐로 주경로를 검사하고, 적·보스·코어·귀환 드론의 안전 위치를 먼저 예약해야 합니다. 적 배치가 실패하면 검증된 대체 위치를 사용하거나 명시적으로 맵을 재생성합니다. 실제 적 수와 계획 적 수를 진단에 남깁니다. 이동 그래프와 보행 충돌은 같은 기준에서 생성하고, 적 경로는 벽을 포함한 도달 가능성을 확인합니다. 코어 회수와 귀환 성공은 한 번만 처리되도록 멱등성을 유지합니다.

맵 교체는 새 지도 검증이 끝난 뒤 기존 지도와 바꾸는 구조가 적절합니다. 현재 `regenerate`는 기존 root를 먼저 해제합니다. 비동기 생성으로 발전시키면 취소된 요청의 결과가 현재 지도를 덮어쓰지 않도록 generation ID를 실제 world 적용 단계에서도 확인해야 합니다.

## 계측과 완료 기준

현재 `performanceStatus`는 출격 누적 평균만 제공하며 첫 로딩이나 멈춘 프레임이 섞입니다. 메인 renderer의 통계만 반환하므로 전체 GPU 비용도 아닙니다. 측정 구간 초기화, 프레임 histogram, p50/p95/p99, 최대 지연, 장면별 태그를 추가합니다. 입력, 이동 충돌, AI, 효과, DOM, render submission을 분리하고 GPU timer 지원 여부도 기록합니다. 지형 수·raycast 후보 수·검사 삼각형 수·활성 물리 body·소리 voice 수를 함께 남기면 원인 비교가 가능합니다. ## 권장 작업 묶음

1. **진행 보호:** 저장 스키마·복구·저장 실패 처리, 거리 맵 연속 충돌, 일시정지와 치명적 오류 복구.
2. **회귀 방지:** 실패 6개 원인 해결, 현행 맵 브라우저 검사, 테스트를 통과해야 배포하도록 연결.
3. **빠른 성능 개선:** 본거지 뒤 렌더 중단, 멀리 있는 구역 업데이트 중단, 행렬 갱신·HUD 작업 축소, 원본 ZIP 배포 제외.
4. **가장 큰 구조 개선:** 충돌 형상·저장 구조 축소, 공간별 raycast, 지도 생성 분할, 구역 스트리밍, 반복 메시 인스턴싱.
5. **환경 대응:** 로딩 순서·에셋 압축, 품질 설정, 효과 예산, 장시간·다중 브라우저·장애 주입 검사.

처음부터 엔진 교체나 WebGPU 전환을 추진할 근거는 부족합니다. 먼저 현재 Three.js 구조에서 확인된 낭비와 정확성 문제를 줄이고, 같은 시나리오에서 효과를 측정하는 편이 낫습니다. 워커 역시 큰 수치 계산과 생성에 우선 적용하고 입력·사격 루프 전체를 한 번에 옮기지 않습니다.
